# خطة التحوّل الهندسي الكبرى — `smarthub`

**تاريخ البناء:** 2026-10-05 · **الأساس:** قياسات فعلية على 965 ملفاً (911 إنتاجياً) · **لم تُعدَّل أي شيفرة**

> هذه الخطة مبنية على رسم اعتماديات كامل (static + dynamic)، وكشف دورات بخوارزمية Tarjan، وقياس نصف قطر الانفجار الانتقالي، وإعادة تشغيل 85 هجرة بالترتيب. كل رقم فيها قابل لإعادة الإنتاج بالسكربتات في `.audit/`.

## المفاجأة التي غيّرت الخطة

قبل القياس كان المتوقّع: 497 ألف سطر، 26 نطاقاً، 82 مساراً ⇒ تشابك عميق يستدعي إعادة هيكلة واسعة.

**القياس قال العكس:**

| المؤشّر | القيمة المقيسة | الحكم |
|---|---|---|
| استيرادات feature → feature | **7 عبارات عبر 5 حوافّ** (من بين 26 نطاقاً) | ✅ ممتاز |
| دورات اعتمادية (SCC > 1) | **2** فقط، إحداهما تافهة (ملفان) | ✅ ممتاز |
| تلوّث متبادل بين النطاقات | شبه معدوم | ✅ ممتاز |
| التسرّب الحقيقي | **56 من 68** مستورِداً مباشراً لـSupabase يخالف القاعدة المكتوبة | ❌ **82% خرق** |
| آليات الإنفاذ | **صفر** قاعدة حدود في ESLint · صفر CI · `verify` = `vitest` فقط | ❌ **لا شيء** |

### الخلاصة الهندسية

> **المشكلة ليست في شكل المعمارية — بل في أنها غير مفروضة، ومركّزة في ستّ عُقد فقط.**
>
> حدود الـFeatures محترمة بنسبة **99.3%** — لكن هذا الاحترام **صدفة انضباط بشري، لا نتيجة بنية**. لا قاعدة واحدة تمنع الخرق. والدليل أن القاعدة الوحيدة المكتوبة صراحةً في `AGENTS.md` («لا استخدام خام لـSupabase خارج `api.ts`») **مخروقة في 82% من المواضع** — لأنها الوحيدة التي كان لها *نص* ولم يكن لها *إنفاذ*.
>
> لذلك: **لا إعادة كتابة. لا إعادة ترتيب مجلدات واسعة.** الخطة = تفكيك 6 عُقد + تركيب طبقة إنفاذ + تحويل التوثيق من أمنيات إلى عقود قابلة للتنفيذ.

**هذا يقلّل حجم العمل بأكثر من 70% مقارنة بخطة إعادة هيكلة تقليدية، ويرفع الأثر.**

# B. المعمارية الهدف (Target Architecture)

## B.1 المبدأ الحاكم

> **كل قاعدة معمارية إمّا أن تكون قابلة للتنفيذ آلياً، أو تُحذف من التوثيق.**
>
> المستودع أثبت عملياً أن القاعدة المكتوبة بلا إنفاذ تُخرَق بنسبة 82%. القاعدة غير المفروضة ليست قاعدة — بل دَين توثيقي.

## B.2 البنية

نُبقي Feature-Sliced Design (هو ناجح فعلياً بدليل 7 حوافّ فقط) ونضيف **طبقة `shared` محكومة** و**عقداً عامّاً لكل feature**:

```
src/
├── app/                    ← جذر التركيب فقط. لا منطق أعمال. لا شيء يستورده.
│   ├── providers/          ← كل Provider، واحد لكل ملف، مرتَّب صراحةً
│   ├── router/
│   │   ├── routes.ts       ← سجلّ مسارات معطى-كبيانات (يحلّ محل 82 JSX يدوياً)
│   │   └── Router.tsx      ← يستهلك السجلّ: lazy + ErrorBoundary + guard تلقائياً
│   └── bootstrap.ts
│
├── shared/                 ← الطبقة الوحيدة التي يجوز للجميع استيرادها. محكومة بالبوابة §G.3
│   ├── ui/                 ← نظام التصميم (28 بدائية حالية) + shared/ui/icon
│   ├── lib/                ← دوال نقية بلا حالة وبلا I/O
│   ├── api/                ← عميل Supabase + تعيين الأخطاء + الأنواع المولَّدة
│   ├── storage/            ← الغلاف الوحيد لـlocalStorage/IDB (مخطط + إصدار + حصة)
│   ├── config/             ← env مُتحقَّق بـZod وقت الإقلاع، مصدر وحيد
│   ├── errors/             ← تصنيف الأخطاء (§M)
│   └── types/
│
└── features/<domain>/
    ├── index.ts            ← ★ العقد العام — المسار الوحيد المسموح للاستيراد من الخارج
    ├── api.ts              ← ★ الموضع الوحيد الذي يلمس فيه هذا النطاق الشبكة
    ├── model/              ← الحالة + قواعد النطاق (نقية قدر الإمكان)
    ├── ui/                 ← المكوّنات والصفحات
    └── types.ts
```

**ملاحظة حاسمة:** الـ14 ملف barrel الميتة لا تُحذف — بل **تُحيا كعقود مفروضة**. هذا يحوّل 14 ملفاً ميتاً إلى آلية الإنفاذ الأساسية بتكلفة شبه صفرية.

## B.3 حلّ العقدة 2 — من Context عملاق إلى مخزن بمُحدِّدات

**التشخيص:** ~60 تفضيلاً قياسياً، كلها في النهاية تكتب **متغيّر CSS**. React Context أسوأ أداة ممكنة لذلك (كل تغيير يُعيد تصيير كل مستهلك).

**الحل — ويُحيي تبعية ميتة بدل حذفها:**

`zustand` مثبَّت فعلاً و`src/stores/*` ميتة. بدل حذف المكتبة، نستعملها لما تجيده تحديداً:

```ts
// shared/preferences/store.ts
export const usePreferences = create<Preferences>()(persist(…, {
  name: 'prefs', version: 3, migrate, partialize,
}));

// القراءة بمُحدِّد ⇒ لا يُعاد التصيير إلا لمن يقرأ هذا الحقل بالذات
const fontSize = usePreferences(s => s.fontSize);

// التطبيق: اشتراك واحد على مستوى الوحدة يكتب متغيّرات CSS — صفر إعادة تصيير
usePreferences.subscribe(applyCssVars);
```

**الأثر المتوقَّع:** سحب شريط تمرير التفضيلات يتحوّل من «إعادة تصيير 50 شجرة» إلى **صفر إعادة تصيير** (كتابة متغيّر CSS فقط).

وتُفصَل المسؤوليات الأربع: `shared/preferences` · `shared/i18n` · `features/account/api.ts` (المزامنة) · `shared/storage` (الاستمرارية).

## B.4 حلّ العقدة 3 — المسارات كبيانات

```ts
// app/router/routes.ts
export const routes: RouteSpec[] = [
  { path: '/chat/g/:chatId', load: () => import('@/features/chat'), auth: 'required', shell: 'full' },
  { path: '/german-club/review', load: () => import('@/features/german-club/ui/Review'), auth: 'admin' },
];
```
`Router.tsx` يشتقّ تلقائياً: `lazy` + `Suspense` + `ErrorBoundary` + الحارس + الـshell.
**النتيجة:** 1424 سطراً ← ~150 سطراً. إضافة مسار = **سطر واحد**. ويصبح `auth: 'required'` **إجبارياً بالنوع** — فلا يمكن إضافة مسار دون قرار صريح بشأن المصادقة (يعالج بنيوياً أن 0 من 82 مساراً محمي اليوم).

## B.5 اتجاه الاعتماديات

```
          app/  ──────────────┐
            │                 │
            ▼                 ▼
      features/<x> ──────► shared/
            │                 ▲
            └── features/<y> ─┘   ممنوع إلا عبر features/<y>/index.ts
```

| القاعدة | الإنفاذ |
|---|---|
| `shared/` لا يستورد من `app/` أو `features/` أبداً | `no-restricted-imports` |
| `features/x` لا يستورد مسارات داخلية من `features/y` | `no-restricted-imports` بنمط `@/features/*/!(index)` |
| لا أحد يستورد `app/` | `no-restricted-imports` |
| `shared/lib` دوال نقية — لا React ولا Supabase ولا DOM | `no-restricted-imports` |
| `@supabase/*` و`shared/api/client` فقط داخل `*/api.ts` | `no-restricted-imports` |
| `localStorage` / `sessionStorage` فقط داخل `shared/storage` | `no-restricted-globals` |
| `import.meta.env` فقط داخل `shared/config` | `no-restricted-syntax` |
| مكتبات الأيقونات فقط داخل `shared/ui/icon` | `no-restricted-imports` |

**ثماني قواعد ESLint تُحوِّل ثماني اتفاقيات شفهية إلى بنية.** هذا جوهر الخطة.

# E. إستراتيجية إعادة الهيكلة — بلا Big-Bang

## المبدأ: **Strangler Fig + ثلاث بوابات لكل خطوة**

1. **قابلة للتحقّق** — فحص آلي يثبت نجاحها
2. **قابلة للتراجع** — PR واحد، `git revert` نظيف
3. **محدودة الأثر** — لا تمسّ أكثر من عقدة واحدة

## القاعدة الذهبية: السقّاطة قبل التنظيف

المستودع يملك سابقة موثّقة لفشل العكس: `designSystem.test.ts` يوثّق رفع الميزانية ثلاث مرات (`351→352→367`)، وميزانية `text-[Nrem]` = 1800 لواقع 170 (هامش 1630 ⇒ لا يمكن أن تفشل)، و`lint-budget` متجاوَز بـ175 ولا يُشغَّل.

> **لذلك: تُركَّب البوابة أولاً عند الرقم الحالي بالضبط، ثم يبدأ التنظيف. البوابة الجديدة هامشها صفر ولا تُرفَع أبداً — تُخفَّض فقط.**

## التسلسل الإجباري

```
Stabilize → Isolate → Refactor → Standardize → Harden → Document → Automate
```

**لماذا `Stabilize` أولاً:** لا يجوز إعادة هيكلة فوق نظام لا يُبنى (`postprocessing` مفقود) وبلا CI (يُدمج تلقائياً بلا فحص). إعادة الهيكلة بلا شبكة أمان = مقامرة.

**لماذا `Isolate` قبل `Refactor`:** لا تُلمَس عقدة قبل أن يُوجَد عقد يحميها. نضع الواجهة أولاً، نحوّل المستهلكين إليها، ثم نُبدّل الداخل خلفها بأمان.
